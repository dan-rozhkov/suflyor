Ты выполняешь задачу **`$ARGUMENTS`** в автопилот-режиме по фиксированному воркфлоу этого репозитория. Работай до конца без остановок на подтверждение (полный автопилот), но соблюдай гейты качества ниже.

## Контекст репозитория

- Suflyor: один git-репозиторий, ветка `main`, **публичный** GitHub. Единственный продукт: веб-страница с живым переводом EN→RU. Весь код в `src/` (страница, `worker.ts` — Cloudflare Worker, тесты рядом), сборка vite в `dist/`, конфиги `vite.config.mts` и `wrangler.jsonc` в корне. Electron и Swift в проекте нет.
- В основном чекауте может работать другая сессия. Вся работа идёт в отдельном worktree, основной чекаут ты не трогаешь.

## Запреты

- Ключи живут в Infisical, файла `.env` нет. Запуск: `infisical run --env=dev -- <команда>`. Не печатай значения и не записывай их на диск: ни в логи, ни в отчёты, ни в сообщения субагентам.
- Репозиторий публичный: транскрипты встреч, имена клиентов и их продуктов, записи звука в него не попадают. Примеры и фикстуры только вымышленные. Перед коммитом просмотри diff на такие данные.
- Не снимай весь экран: только страницу приложения. На полноэкранном снимке окажутся личные данные.

## Шаги

### 0. Worktree
Придумай короткий `<slug>` задачи (латиница, kebab-case). Создай worktree от свежего `origin/main` рядом с репозиторием:

```bash
R=$(git rev-parse --show-toplevel)
W=$(dirname "$R")/wt-auto-<slug>
git -C $R fetch origin
git -C $R worktree add -b auto/<slug> $W origin/main
```

- `node_modules`: если `package-lock.json` в worktree совпадает с основным чекаутом — симлинк `ln -s $R/node_modules $W/node_modules`; иначе `npm ci` в worktree.
- Проверки с настоящими API запускай из worktree через `infisical run --env=dev -- <команда>`: `.infisical.json` уже в репозитории.
- Все команды, правки, субагенты, ревью — только с путями внутри `$W`. Bash сбрасывает cwd, поэтому пиши абсолютные пути или `git -C`.

### 1. Брейншторм / план
Если задача содержит хоть каплю неоднозначности в требованиях или дизайне — сначала вызови `superpowers:brainstorming`, затем при необходимости `superpowers:writing-plans`. Для явно механических/точечных правок можно пропустить и сразу идти к делу, кратко назвав план.

### 2. Делегируй субагентам на Sonnet
- Реализацию отдавай через `Agent` **с `model: "sonnet"`**, `subagent_type: "general-purpose"` (или `Explore`/`Plan` где уместно).
- **Независимые** куски запускай параллельно — несколько `Agent`-вызовов в одном сообщении. Обычное разделение: страница (`app.ts`, `app.css`, `index.html`) и Worker. Зависимые — последовательно. Параллельным субагентам давай **непересекающиеся** файлы; если пересечение неизбежно (например `src/types.ts`) — запускай последовательно.
- В промпте субагенту зашей: абсолютный путь worktree и запрет трогать основной чекаут, запреты выше, точный скоуп, какие файлы трогать, команды проверок (см. шаг 5, дословно), и что вернуть (список изменений + результаты проверок **с числом файлов/тестов**). Субагенты **не** делают git-операций — коммит и пуш только основной агент (ты).

### 3. Ревью через /code-review
После сборки изменений вызови `Skill` с `code-review` (эффорт по масштабу: `medium` для точечных, `high` для крупных). Явно передай цель: путь worktree и `git -C $W diff origin/main`. Если в шапке отчёта не тот репо или коммит — выбрось отчёт целиком и перезапусти.

### 4. Почини находки
Реальные замечания ревью почини (сам или новым Sonnet-субагентом). Отсеивай ложные — не чини вслепую (`superpowers:receiving-code-review`). Повтори ревью, если правки существенные.

### 5. Верификация перед коммитом
Внутри worktree прогони каждую проверку **отдельной командой** с выводом в файл и явным кодом возврата (пайп `| tail` прячет красный код):

```bash
cd $W && npm run typecheck > $SCRATCH/typecheck.txt 2>&1; echo "typecheck=$?"
cd $W && npm test > $SCRATCH/test.txt 2>&1; echo "test=$?"
cd $W && npm run build > $SCRATCH/build.txt 2>&1; echo "build=$?"
```

- Линтера в проекте нет. `npm run build` собирает сайт в `dist/`.
- **Никогда** `npm test -- run`: это фильтр по имени. Сверяй число файлов/тестов с прошлым прогоном.
- Задача про распознавание, перевод или подсказки: юнит-тестов мало. Прогони реальный Soniox через конвейер сайта в Chromium с поддельным микрофоном (записанный звук подаётся вместо микрофона) и сравни результат с прошлым прогоном. Ключ передавай через `infisical run` в процесс локального сервера, который импортирует `src/worker.ts` и вызывает его со своим `env`: `wrangler dev` без `.dev.vars` секретов не видит, а `.dev.vars` нарушил бы запрет писать ключи на диск. Не печатай ключ. Записи и транскрипты держи только в `$SCRATCH`.
- Задача про звук, разрешение микрофона или установку на iPhone: в Chromium это не проверить до конца. Что нельзя проверить без живого телефона, прямо назови в итоге.

Не заявляй «готово», пока не увидел зелёный вывод (`superpowers:verification-before-completion`). Если что-то красное — вернись к шагу 4.

### 6. Commit + push в main (делаешь ты, основной агент)
В worktree:
- `git status --short`, стейджи **перечислением путей**, никогда `-A`/`.`.
- Осмысленное commit-сообщение на английском. В конце — строки атрибуции из системного напоминания текущей сессии.
- `git fetch origin`, затем `git rebase origin/main` **отдельной командой**. Проверь код возврата и что `git status` не показывает «rebasing». Если main сдвинулся — снова шаг 5.
- Пуш: `git merge-base --is-ancestor origin/main HEAD && git push origin HEAD:main`.

### 7. Скриншоты
Отчёт в Notion получает **только запушенный** код — сначала шаг 6, потом этот шаг.

Сними скриншоты того, что сделано, из worktree. Сохраняй PNG в `$SCRATCH/auto-<slug>/`, имена `NN-<что-на-снимке>.png`.
- **UI-изменение**: собери сайт (`npm run build`) и отдай `dist/` любым статическим сервером на своём порту (`5199`), открой headless Chrome через CDP, задай окно 390×844 через device-metrics override, иначе Chrome обрежет страницу. Нужное состояние (форма кода, панель установки, лента) получай действиями на странице; если нужен текст в ленте — подставь вымышленный, фикстур в репозитории нет. Открой каждый PNG через `Read` и убедись, что на нём то, что нужно, а не белый экран или страница ошибки. Останови запущенные процессы.
- **Без UI** (Worker, чистая логика): вставь в отчёт блоком кода вывод проверок или сравнение прогонов.

### 8. Страница в Notion
Одна страница на задачу. Повторный `/auto` по той же задаче **обновляет** её, а не создаёт новую. Если у проекта уже есть страница со скриншотами, новая задача дописывается туда отдельной секцией.

1. Найди страницу: URL из аргумента `notion:<URL>`; затем страница проекта из памяти; иначе `notion-search` по `auto-slug: <slug>` и по названию задачи. Нашёл — `notion-fetch` и обновляй. Не нашёл — создавай.
2. Залей каждый PNG: `notion-create-file-upload` с `filename`, затем **один** multipart POST на `upload_url` со всеми `upload_headers` (`curl -sS -X POST "$URL" -H '...' -F "file=@<png>"`). Из ответа бери `suggested_markdown`. Загрузка живёт около часа — вставляй на страницу сразу.
3. Содержимое (Notion-markdown, сначала прочитай `notion://docs/enhanced-markdown-spec`):
   - первая строка: одно-два предложения, что сделано; затем `Код в main:` short SHA коммита; условия снимков (размер окна, фикстуры);
   - секции `##` по смыслу, в каждой — картинки с подписью-описанием, что на снимке;
   - `## Что изменилось` — маркированный список для человека, не для разработчика;
   - `## Проверки` — typecheck/test/build с числом тестов;
   - последняя строка серым: `auto-slug: <slug>` (по ней шаг 8.1 найдёт страницу).
4. Создание: `notion-create-pages` с `creation_mode: "draft"` (приватная страница), иконка-эмодзи, заголовок `<Задача> (DD.MM.YYYY)`. Обновление: `notion-update-page` — для нового прогона допиши секцию `## Обновление DD.MM.YYYY` через `insert_content`. Не удаляй старые снимки без причины.

### 9. Уборка и итог
- `git worktree remove $W` (сначала удали симлинк `node_modules`), `git branch -D auto/<slug>`. Если worktree грязный — не удаляй, сообщи почему.
- Итог в чат кратко: что сделано, short SHA, ссылка на страницу Notion, что не проверено и что отложено. Если по ходу всплыло что-то важное для памяти проекта — предложи записать.

## Правила
- Заблокирован (нужен доступ/решение только пользователя, задача расходится с фактами кода) — **остановись и спроси**, не выдумывай обходной путь.
- Не снижай пороги тестов ради зелёного прохода. Не давай субагентам делать `git stash/reset` и не трогай основной чекаут.
- `$SCRATCH` — scratchpad-директория сессии из системного промпта.
